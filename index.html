What the Adder Learned

A small transformer, built for the job, adds numbers a few digits longer than any it was trained on. Carry the One asked how to build it. This post opens it up. Recording its state after every round of computation, probing what each digit position knows, following attention, and swapping states between runs gives a consistent picture: every digit does its own arithmetic at once, a carry then moves along the number one place at a time, and the answer slowly settles. The same measurements explain two of its failures and pointed to a training change that removes one of them. A final test shows that change moved the limit; it did not remove it.

The model from Carry the One reads two numbers, writes each into a fixed set of slots, repeats one transformer block over those slots, and reads the sum back out. It was trained on operands of up to 20 digits and is exact at 21; what it was not asked to do is explain itself. Its computation is small enough to take apart: one block, repeated, with a handful of numbers on every digit position at every round. I wanted to know what the block is doing in those rounds, and whether knowing that would say anything useful about where the model fails.

Findings at a glance

  1. Time to a correct answer tracks the number of digits, not the longest carry chain (correlation 0.93 against 0.33 in v22).
  2. Each place computes in a fixed order: its own digit sum and its own carry-out within the first two rounds, then whether a carry arrives, then the final digit. The place that is right last is usually where a carry chain ends (9 of 12 crafted chains; in the rest, where it starts).
  3. The carry travels one place at a time. Attention concentrates on the next place down (about 19% of a place’s attention in a 16-digit problem). Along a run of nines a carry advances about 1.85 rounds per place. That is linear in the length of the chain; I found no sign of carry-lookahead.
  4. The carry is a real, readable quantity. Swapping one place’s state from a run where a carry arrives into a run where it does not changes that place’s answer digit by exactly one (swapped in at round 14, 100% of 240 problems), and changes nothing else.
  5. The four scratch tokens are not interchangeable. Replacing token 0 breaks every length; token 2 can be zeroed with no effect; token 3 matters more the longer the problem. Together they carry the problem’s length (98% decodable) but not its carry statistics.
  6. The model never reaches a fixed point. v22’s state keeps moving in one direction after the answer is right, and, depending on the length of the problem, somewhere between round 25 and round 50 it leaves the answer behind. Training with a random number of rounds removes that within the lengths it was trained on.
  7. The fix has a boundary. v33 is at 99.5% or better through 64 digits (its training limit), 99.0% at 72 and 74.5% at 80. Running it 60 rounds longer changes nothing, so the limit is how long a problem the model was trained on, not how long it computes.

The model

Numbers go in as digits, one per place, units first. Each digit becomes three numbers (one of ten learned “codewords”) written into that place’s own slot, so place 7 always means the same three of 384 dimensions no matter how long the number is, and short numbers are padded with zeros out to 30 places. The combiner then turns each place’s two codewords into a vector (a “place token”), adds four learned scratch tokens (called thinking tokens in the code), and applies one transformer block — six-head attention that every token can use on every other, then an MLP — again and again with the same weights. After the last round each place’s vector is cut back to three numbers and read as the nearest codeword. The last step has no parameters, and the first has about forty; the arithmetic is all in the repeated block.

The three checkpoints used here, all from the same family, all trained on freshly generated problems (30% built to contain long carry chains):

  • v23: v22 continued with a random number of rounds on every batch (anywhere from as many rounds as the problem has digits up to 24) instead of always 24. Iteration 10,500.
  • v33: the same idea with up to 80 rounds, 128 place slots, and operands up to 64 digits, continued from v22. Iteration 15,000.

How the model was opened

Everything below rests on a few small instruments. I added three inert hooks to the model: one records the full state after every round, one lets a function rewrite the state between rounds, and one records the attention weights. Every measurement below was run on a CPU.

  • Reading the answer early. The model’s own readout is applied to the state after round k for every k: “what would the answer be if we stopped here?” Round 0 is the state before the first round. v22 was never trained to be read before its last round, so early readouts are rough; they are measurements of the state, not of intent.
  • Linear probes. A least-squares classifier (ridge, fixed penalty) on a place token’s 384 numbers, trained on 70% of 500 problems and scored on the other 30%, split by problem. The 500 problems have 2–18 digits: a quarter with two operands of the same length, a quarter of different lengths, half with a run of nines. Each result is compared against always guessing the most common answer.
  • Attention maps from the block, averaged over its six heads and over 24 problems of each kind.
  • State swaps (activation patching, as in causal tracing): replace one place’s state at one round with the state from a second run on slightly different operands, and see what the answer does.
  • Ablations of the scratch tokens: set a token’s starting value to zeros, or to the average of the other three.

Rounds are counted from 1 for the first application of the block. Where a chart says “round 0” it means the state before any round. The fixed test sets and the length test (last section) use one operand of the stated length and the other of any length up to it. In the attention maps and scratch-token probes, “random” means two operands of the stated length and “nines” means a number ending in a run of nines plus a shorter random number. “Carry-heavy” problems are built the way the training generator builds them, with a long run of nines in one operand and a nonzero units digit in the other.

The time it takes tracks length, not the carry chain

For each problem, find the first round after which the model’s answer stops changing. Across random problems that round correlates almost perfectly with the number of digits (0.93 in v22) and weakly with the longest carry chain in the problem (0.33). The chains are short on average (2.5 places in this sample), so the model is mostly not waiting for a long carry to arrive. One reading is that it is waiting to be sure there is none; I did not test that.

A trap in the obvious test

The simplest carry test, 99…9 + 1, is answered correctly by round 8–13 in v22 for every length from 4 to 24 digits, which would look like carries that cost nothing. It is not. The training generator produces exactly that pattern (a full run of nines is one of its cases), and a run of nines in the middle of a number is a much slower case, below. I read the 99…9 + 1 result as a learned fast path for one input, not as evidence about carries in general.

What each place computes, and in what order

A linear probe on a place token at each round shows an order of operations. Before any round the token holds just its two digits; (a + b) mod 10 is not yet readable (63%, against 62% for always guessing the commonest digit). One round later it is (97%). The carry-out is mostly decided by the place’s own two digits and is readable almost immediately. Whether a carry arrives takes several rounds, and the final digit, which needs all of it, comes last.

v22. Held-out accuracy of a linear probe on a place token, from 500 problems (the mix described above). Always guessing the commonest answer scores 62% for the digit sum, 78% for carry-out and carry-in, and 65% for the answer digit. By round 8 the digit sum is read correctly for 100% of places and carry-in for 99.8%; the answer digit reaches 98% by round 12 and 99.8% by round 16.

The picture sharpens when places are sorted by what the carry does to them. A place inside a chain, or with no carry, is already 85%–89% readable at round 2. A place where a carry starts is 44% readable at round 2 and 88% at round 8. A place where a carry ends is the slowest: its answer digit is not readable at all at round 0 and only 37% readable at round 4. All four kinds are above 99% by round 16.

answer digit, by kind of place

The carry-in probe is more telling. At the end of a chain the true carry-in is always 1, yet at round 1 the probe says 0 for almost every place (4% right, against 78% for guessing). Those places are not uncertain; their state confidently says “no carry”, and it takes the carry arriving from below to correct it.

carry-in, by kind of place

v22. “No carry” and “inside a carry” places are right early; the two ends of a chain are not. Places beyond the length of the number (not drawn) are right from round 0.

The carry moves one place at a time

Attention says how. At round 7 the strongest attention in the block goes to the next place down, in all eight kinds of problem tried (random and runs-of-nines, 6 to 20 digits). In a 16-digit random problem 19% of a place’s attention goes there, against at most 2% for any other single place within four. That is the place its carry-in comes from, and the direction is one-way: per place, 27% of attention goes to lower places and 7% to higher ones.

v22. Share of a place token’s attention by how far, in places, the attended token is from it, averaged over six heads and 24 problems, restricted to places inside the number. On a run of nines the band widens to the next two or three places down while the carry is in transit (round 7), then narrows again (round 17).

The four scratch tokens behave differently. In round 1 place tokens look mainly at themselves (45% of their attention). In rounds 2 to 4 they send 41%, 45% and 43% of it to the scratch tokens (16-digit problems), and the scratch tokens send 66% of theirs back to the place tokens in round 2. By round 11 the place-to-scratch share has fallen to 11%. On long inputs it rises again late: to 25% on 20-digit runs of nines at round 21, after dipping to 5%.

v22. Share of a place token’s attention that goes to the four scratch tokens.

Is the carry a real variable?

Probes and attention describe; swapping states tests. Take a 14-digit problem where some place p has no carry coming in and whose two digits sum to 2–6 (so one more cannot carry on), and make a second run in which the place below p is forced to produce a carry. At some round, copy the second run’s state for place p into the first run and carry on. If p’s state really holds the carry, its answer digit should go up by exactly one and nothing else should move.

v22, 240 problems, p between 4 and 10. Swaps before round 6 do nothing, presumably because the second run has not yet worked out its own carry. By round 14 every swap raises the digit by one, none changes the next place up, and no other place changes. As a control, swapping the state of a place three below p at round 4, where the two runs agree, left every answer unchanged.

So by round 10 or so a place’s state carries the carry-in in a form the readout uses. The negative results matter as much. The same swap into the bottom of a run of nines at rounds 12, 14 and 16 does flip that place, but none of the six places above it ever followed (at rounds 8 and 10 not even that place flipped). A second attempt added a “carry-in direction” (the difference between the average states with and without a carry, at 0.5, 1 and 2 times a token’s typical size) at rounds 3, 5, 8 and 12; no place in the run flipped, in any of the 160 problems, in any setting. The carry cannot be injected mid-way and have the block carry it on. It behaves like a trajectory that unfolds from the real operands, not a procedure that can be re-entered. That is a statement about these two ways of injecting a carry, not a proof that no other way exists.

Without any patching, the natural speed of a carry can be read from paired runs: a number with a run of nines, with and without a 1 added at the bottom, decoded at every round.

v22, 200 of 200 problems carried all the way; runs of 7–11 nines in the middle of a 14-digit number, each place’s digit first becoming 0 and staying there. The unpatched controls decoded as a clean run of nines in 73% of cases. The first three places behave irregularly; from place 3 on the ramp is straight.

The fit gives 1.85 rounds per place over all places, 1.6 from place 3 on, with about 5 rounds of start-up. At that speed 24 rounds reach about the tenth place of a chain, so a long mid-number carry does not fit in v22’s budget, and the cost is linear in the length of the chain. A carry-lookahead adder would be logarithmic. I did not find one here. The wavefront of attention at offset −1 is what a ripple looks like once all the places run at once.

Replacing all four tokens by either also gives 0% everywhere. Token 0 cannot be replaced by either: the model gets nothing right, at any length. Token 2 can be removed with no loss (accuracy on the 24–26 digit set was unchanged or a little higher, within the noise of 200 problems). Token 1 is hurt less by the average of the others than by zeros. Token 3 costs more the longer the problem.

Attention is consistent with that. In the first ten rounds token 0 receives the most attention from place tokens (up to 22% of a place token’s attention on a 16-digit problem, against at most 12% for the others). From round 4 to 9 on 20-digit runs of nines, token 3 receives the most of the four (up to 19%). Token 1 reads the place tokens as heavily as the others do, but is almost never read by them (at most 7%).

What do they hold? A linear probe on the four tokens together reads the number of digits in the problem almost perfectly by round 4 (98%; always guessing the commonest length would score 9%), and reads the total number of carries (32% at round 8, against 15%) and the longest chain (29%, against 21%) barely better than guessing. They carry the length of the problem, not its carry statistics. I read “shared channel for the length” into that; it is an interpretation, and I did not open the circuits.

The answer never settles

Run v22 longer than the 24 rounds it was trained for and accuracy does not stay put:

v22, 150 random problems per length set; curves are means over those problems, so heights differ from the full test sets by a few points (the 19–21 digit set reads 97% at round 24 here and 100% on all 600 test problems). The shapes are the point.

Each length set rises, plateaus, and falls, later for shorter problems. Longer problems need more rounds to reach their plateau: the 14–18 digit set first reaches 99% at round 20, against round 14 for 1–10 digits. The 24–26 digit set peaks at round 25 with 83%, just past the trained 24, and is at 6% by round 64. This is why the readout round matters, and it fits a simple reading of v22’s weakness at 25–26 digits (80% and 52%): one or two more rounds would help, and then the drift would take it back. That reading is consistent with the curve; I did not run an intervention that isolates it.

The state does not settle to a point. After the answer is already right it keeps travelling in one direction at a small but non-zero rate: about 2%–5% of its own size per round between rounds 24 and 64 (more, 12%, for the 24-nines problem at round 24, where the carry is still in transit). For a while that is invisible because the decision boundaries are far away; in v22 it eventually crosses them. Block weights shared across rounds do not on their own give you an equilibrium (compare deep-equilibrium models, which solve for one); they give you a trajectory, and a trajectory is read at a time.

v23 changes only how the block is trained: each batch uses a random number of rounds, from as many as the problem has digits up to the full budget, so the block is regularly asked to keep a right answer right.

v23, 150 random problems per length set.

The shorter lengths now hold flat to round 64, and the answer arrives earlier (mean round 11.4, against 16.3; on 1–10 digit problems round 7 against 14). The state still drifts at about the same rate; it just does not reach a decision boundary. The cost is real. On the 24–26 digit set v23 is worse than v22 (64.5% against 77.3%), and still falls with extra rounds. A model that converges fast and holds is a model that holds a wrong answer if a long carry has not finished.

Where the fix runs out

Carry the One says that raising the training range moves the wall rather than removing it: v33, trained to 64 digits, is exact through 26 only because 26 is inside its range. Here is the direct test. v33 is at 99.5% or better at its training limit of 64 digits, still at 99.0% (random) and 99.5% (carry-heavy) at 72, eight digits (12.5%) past it, and falls off after that: 74.5% at 80, 56.5% at 96. Random and carry-heavy problems fall together up to about 96 digits, so up to there this is length, not carries. Past it carry-heavy problems collapse much faster (5.5% against 36.0% at 112 digits).

Giving the model 60 more rounds changes nothing: no length moves by more than 1.5 points. By round 80 the model has finished and then holds its answer, which for these lengths is wrong. The limit is not how long the block runs. It is how long a problem the model was trained on, which is the claim in Carry the One, now measured.

The same shape shows up in both models. v22 was trained to 20 digits and v33 to 64. In each, accuracy starts to break about a quarter past the longest training problem: v22 is 99.0% at 24 digits (+20%), 80.5% at 25 (+25%) and 52.5% at 26 (+30%); v33 is 99.0% at 72 (+12.5%) and 74.5% at 80 (+25%). Two models are a coincidence, not a law, but it is consistent with a model whose computation is sound and whose sense of “how long a number can be” ends where its training did. As a back-of-envelope, 74.5% exact on an 80-digit answer is about 99.6% per digit if errors were independent; the model is nearly right everywhere, and exact match is unforgiving at length.

Limits

  • One task, one model family, one training run per checkpoint. No seed variation; the differences between v22, v23 and v33 are single runs.
  • The probes are small. Linear probes use 500 problems (150 held out) and a fixed ridge penalty, so their accuracies carry a few points of noise. The round-by-round accuracy curves use 150 problems per length set (60 for v33), enough for shapes, not for the third digit of any percentage. Early-round readouts apply a readout the model was not trained to be read at.
  • Attention is averaged over six heads, and I did not open the MLP. The “scratch-token roles” are read from ablations, attention and probes, not from a traced circuit.
  • The state-swap result is positive for one kind of swap (a whole place state, after round 10) and negative for two others. The negative results do not show the carry cannot be injected, only that these two ways failed.
  • The wavefront speed comes from one family of inputs (runs of 7–11 nines in a 14-digit number), and 27% of its unpatched controls were not decoded as a clean run of nines.
  • v33 changed three things at once from v22/v23, and the variable-round change was the only one run alone. I make no claim about which of the other two it needs.
  • For v33 the training script’s own “best checkpoint” (by a clipped validation loss) stopped at iteration 3000 and did not track accuracy. Every v33 number here is from the final iteration-15,000 snapshot.
  • In v33_dynamics.json the keys acc_at_24 and acc_at_64 mean “at the model’s own round budget” and “at budget + 40” (80 and 120 for v33). The charts and tables here are computed from the full per-round curves, not from those keys.

What I would try next

All of this is untested. The training-length result suggests the model needs a reason not to treat the longest length it saw as the longest possible. Two ideas follow from the measurements. One is to remove the fixed ceiling: draw the maximum length per batch from a wide range, so no consistent “answers stop here” is ever learned. The other comes from the attention maps: only the next place down and the scratch tokens carry much attention, yet every place attends over every other place, so a place’s share of attention to its neighbour could fall as numbers get longer. Within the lengths measured here (6 to 20 digits, v22) it does not obviously do so, but I have not measured it past the training length, which is the first thing to check. If it does fall, restricting the block to a local window plus the scratch tokens would make that share independent of length. A caution: in the single-token experiments of the companion post, restricting attention to a local band did not sharpen it, so I would not assume it carries over. A cleaner test of the training-length result is to vary the training maximum alone, holding everything else at v33.

Where this leaves things

The block is doing sound arithmetic. It does not know when it should stop being right.

Taking the model apart shows an algorithm anyone would recognise: each digit does its own sum, a carry moves up the number a place at a time, and the answer settles. It also shows why the model fails: a state that drifts if read too late, a round budget that is tight for the longest problems, and a training length that sets the edge of the numbers it trusts. One of those is fixed by a change in how it is trained. The edge moved with the training range, in both models; it did not go away.
